# Soul Rush

## 프로젝트 소개

> 소울라이크 전투에 뱀파이어 서바이벌류의 런(run) 성장을 얹은, 최대 3인 협동 로그라이크 보스러시

보스를 잡을 때마다 능력 카드를 하나씩 골라 강해지고, 포탈로 다음 층에 올라가 더 강해진 보스와 다시 싸우는 구조의 PC 멀티플레이 게임입니다. 3인 팀 프로젝트로 약 4개월간 개발했으며, 저는 **팀장이자 보스 시스템 · 서버/백엔드 연동 · 로그라이크 진행 구조 · 런타임 최적화**를 맡았습니다.

실시간 전투 동기화(Photon Fusion)와 영속 데이터(Apache · PHP · MySQL)를 **두 개의 독립된 서버 채널로 분리**한 것이 이 프로젝트의 구조적 특징이고, 제가 담당한 부분의 대부분이 이 두 축 위에 있습니다.

## 주요 구현 내용

### (아키텍처) 보스 로직 / 연출 분리 — 호스트 권한 모델

#### 개요

3인이 같은 보스를 상대하는데, 보스 AI를 각 클라이언트가 그대로 돌리면 같은 공격에 대해 데미지가 인원수만큼 중복 적용되고 페이즈·어그로 같은 상태가 클라이언트마다 어긋납니다. 그렇다고 모든 연출까지 호스트가 RPC로 지시하면 통신량이 커지고, 지연이 그대로 애니메이션 끊김으로 보입니다. **이를 해결하기 위해** 보스를 "상태를 확정하는 로직"과 "그 상태를 보고 재생하는 연출"로 클래스 레벨에서 나누고, 로직은 호스트만, 연출은 각 클라이언트가 로컬로 돌리도록 설계했습니다.

#### 설계

- **`NetworkBossCore`(NetworkBehaviour)가 상태의 유일한 확정 지점**
  - 체력·페이즈·어그로 대상·패턴 인덱스·상태 타이머를 전부 `[Networked]`로 두어, 호스트가 계산하면 나머지는 결과만 받게 함
  - 보스 3종(Dragon · PolarDragon · OrcAssassin)이 이 클래스를 상속 — 팀원은 구체 타입을 몰라도 `NetworkBossCore` 하나로 다형적으로 접근
- **`IBossVisual`은 "연출 계약"만 정의**
  - `PlayWakeUp` / `PlayPhaseTransition` / `PlayGroggy` / `PlayDie` 등 재생 명령만 노출하고, 판단은 일절 하지 않음 **(SRP)**
  - 연출은 동기화 대상이 아니라 **동기화된 상태를 각자 해석한 결과**이므로, 애니메이션 자체는 네트워크를 타지 않음
- **데미지는 클라이언트가 요청하고 서버가 검증**
  - `RPC_TakeDamage`는 `RpcSources.All → RpcTargets.StateAuthority`라 누구나 호출할 수 있어, 조작된 클라이언트가 비정상 값을 보낼 수 있음
  - 서버 쪽에서 한 방 최대치를 `maxHP` 비율로 클램프하고 음수(보스 회복 치트)도 차단
- **패턴 진행도 상태로 표현**
  - 현재 패턴 인덱스 / 스텝 인덱스 / 커브 진행값까지 `[Networked]`로 두어, 원격 클라이언트도 "지금 몇 번째 동작의 몇 % 지점인지"를 스스로 계산 — 연출용 RPC를 별도로 쏘지 않아도 융단폭격 같은 긴 패턴이 동일하게 재생됨

#### 관련 코드 / 처리 흐름

```csharp
[Rpc(RpcSources.All, RpcTargets.StateAuthority)]
public void RPC_TakeDamage(float damage, float groggyDamage = 10f, NetworkObject attacker = null)
{
    if (CurrentState == BossState.Die || CurrentHP <= 0) return;

    // RpcSources.All이라 조작된 클라이언트가 999999를 보낼 수 있다 → 서버에서 상·하한을 자른다
    damage      = Mathf.Clamp(damage,      0f, maxHP * maxSingleHitPercent);
    groggyDamage = Mathf.Clamp(groggyDamage, 0f, maxGroggy);

    float finalDamage = damage * GetIncomingDamageMultiplier();
    if (CurrentState == BossState.Groggy) finalDamage *= groggyDamageTakenMultiplier; // 딜 타임 보상

    float applied = Mathf.Min(CurrentHP, Mathf.Max(0f, finalDamage));
    CurrentHP -= finalDamage;
    _aggroTracker.Record(attacker, applied);   // 어그로 장부는 페이즈 판정보다 먼저 기록
}
```

> 📸 **[다이어그램]** 클래스 다이어그램 — `NetworkBossCore`(호스트 전용) ↔ `IBossVisual`(각 클라이언트) 경계선과, 3종 보스가 어느 쪽을 상속/구현하는지가 보이게

### (보스 AI) ScriptableObject 패턴 모듈과 전용 프리뷰 툴

#### 개요

보스 공격 패턴을 코드로 작성하면 패턴 하나를 추가하거나 사거리·가중치를 조정할 때마다 스크립트를 고치고 다시 컴파일해야 합니다. 더 큰 문제는 검수였는데, "칼을 내려찍는 순간에 소리가 나는지" 같은 타이밍을 확인하려면 매번 게임을 실행해 보스를 그 패턴이 나올 때까지 유도해야 했습니다. **이를 해결하기 위해** 패턴을 ScriptableObject 조립 단위로 만들고, 인스펙터 안에서 패턴 전체 시퀀스를 사운드와 함께 재생·스크럽할 수 있는 전용 에디터 툴을 제작했습니다.

#### 설계

- **`BossActionModule` = 단위 동작 한 칸**
  - 애니메이션 State 이름 · 지속 시간 · 이동량(`moveOffset` + `moveCurve`) · 히트박스 인덱스 · 슈퍼아머 · 트래킹 정지 시점 · 사운드 재생 시점을 한 구조체에 담음
  - `duration`을 원본 클립 길이와 다르게 줄 수 있게 해서, 애니메이터를 건드리지 않고도 후딜레이·엇박자를 조절
  - `moveCurve`(0~1 → 0~1)로 돌진 가속을 그래프로 깎게 함 — 급발진·멈칫 후 돌진을 코드 없이 표현
- **문자열 State 이름은 `OnValidate`에서 해시로 미리 변환**
  - 인스펙터에서 값이 바뀔 때만 `Animator.StringToHash`를 돌려 저장 → 런타임 문자열 해싱 비용 0
- **`BossPatternModule` = 액션 시퀀스 + AI 조건**
  - `minRange` / `maxRange`로 후보를 거른 뒤 `weight`로 가중치 추첨 → 같은 보스라도 매번 패턴 순서가 달라짐
  - 1페이즈 / 2페이즈 패턴 리스트를 따로 두고, 페이즈 전환 시 **리스트 자체를 교체**해 광폭화를 표현
- **전용 인스펙터 툴(623줄)로 검수 비용을 제거**
  - `PreviewRenderUtility`로 보스 프리팹을 인스펙터 안에서 렌더하고, 패턴의 액션들을 처음부터 끝까지 **순서대로** 재생 (▶/⏸, 타임라인 드래그 스크럽, 반복)
  - 각 액션의 `actionSoundPercent` 지점을 지날 때 실제 `actionSound`를 재생 → 게임에서 들리는 것과 같은 순서·타이밍으로 사운드 검수 가능
  - 프리뷰용 프리팹 선택은 `EditorPrefs`에 저장 — 에셋에 남지 않아 커밋되지 않고 팀원마다 각자 고름
  - Animator가 중첩 프리팹(FBX) 안쪽 자식에 있어 루트에 `SampleAnimation`을 호출하면 커브 경로가 어긋나므로, Animator가 붙은 오브젝트를 따로 찾아 샘플링하도록 처리

> 📸 **[에디터 툴]** ★최우선 — `BossPatternModule` 인스펙터 프리뷰 화면. 보스 모델이 렌더되고 타임라인·▶/⏸ 버튼·액션별 사운드 마커가 함께 보이게

> 📸 **[스크린샷]** 패턴 SO 인스펙터 — `minRange`/`maxRange`/`weight`와 액션 시퀀스 리스트가 펼쳐진 상태

### (전투) AoE 장판 판정과 누적 딜량 기반 어그로

#### 개요

보스의 광역기는 파티클 연출과 실제 피격 판정의 타이밍이 어긋나면 "이펙트는 이미 사라졌는데 맞는다"는 식으로 곧바로 체감됩니다. 또 협동 게임에서는 보스가 누구를 쫓는지가 재미의 핵심인데, 단순히 가장 가까운 사람을 쫓게 하면 뒤에서 딜을 넣는 플레이어가 전투에 관여하지 못합니다. **이를 해결하기 위해** 파티클 재생 시간에 동기화되는 다중 구간 판정 컴포넌트와, 누적 딜량을 기록해 주기적으로 어그로를 재계산하는 추적기를 따로 만들었습니다.

#### 설계

- **하나의 이펙트 안에 여러 판정 구역을 시간축으로 배치**
  - `AoEHitZone`(형태 Sphere/Box · 크기 · 오프셋 · `startTime` · `duration`) 리스트로 연쇄 판정을 구성 — 브레스가 앞에서 뒤로 번지는 식의 연출을 판정으로 그대로 옮김
  - `syncParticle`을 지정하면 파티클의 실제 재생 시간에 판정 구간을 맞춤
- **판정은 전원이, 데미지는 권한자만**
  - 모든 클라이언트가 로컬로 오버랩을 돌려 **피격음과 히트 위치 연출**을 각자 재생하고, 실제 체력 차감은 `_damageEnabled`가 켜진 호스트만 수행
  - 덕분에 인원수만큼 데미지가 중복되지 않으면서도 타격감은 전원이 동일하게 느낌
- **매 프레임 도는 판정이라 할당을 없앰**
  - `Physics.OverlapSphereNonAlloc` / `OverlapBoxNonAlloc` + 고정 크기 버퍼(16)로 프레임마다 배열이 새로 할당되며 생기던 GC 스파이크 제거
- **`BossAggroTracker`를 순수 C# 클래스로 분리**
  - 누적 딜량 장부는 네트워크 동기화가 필요 없는 호스트 로컬 데이터이므로 `NetworkBehaviour`에서 떼어냄 — 보스 코어의 책임이 줄고, 네트워크 없이 단독 검증 가능 **(SRP)**
  - 일정 주기마다 최다 딜러를 뽑아 어그로를 옮기고 장부를 비움. 이때 `PlayerRegistry.IsAlivePlayer`로 **살아 있는 플레이어만** 후보에 넣어, 다운된 팀원에게 어그로가 묶이는 상황을 차단

> 📸 **[다이어그램]** 어그로 루프 4단계 — 피격 기록 → 주기 만료 → 최다 딜러 산출(사망자 제외) → 어그로 동기화 + 장부 초기화

> 📸 **[스크린샷]** AoE 판정 구역 기즈모 — 씬 뷰에서 `hitZones`가 시간차를 두고 배치된 모습

### (서버) Unity ↔ PHP / MySQL 백엔드 연동

#### 개요

스킬 밸런스 수치가 클라이언트 에셋에 박혀 있으면 쿨타임 하나를 고칠 때마다 빌드하고 팀원 전원이 다시 받아야 합니다. 반대로 애니메이션·VFX·히트박스처럼 에셋에 붙어 있는 값까지 서버로 올리면 통신 규격만 비대해지고 얻는 게 없습니다. 여기에 더해, 발표장과 집의 네트워크 환경이 달라 서버 주소를 하나로 고정할 수도 없었습니다. **이를 해결하기 위해** 데이터를 성격에 따라 로컬 에셋과 DB로 나누고, 클라이언트가 실행 시점에 접속 환경을 스스로 판별하도록 구현했습니다.

#### 설계

- **하이브리드 데이터 분리 — 무엇을 서버에 둘지의 기준을 먼저 정함**
  - **DB**: 쿨타임 · 스태미나 소모 · 레벨별 배율 · 최대 레벨 · 등장 스테이지처럼 **숫자만 바뀌는 밸런스 값**
  - **로컬 에셋**: 애니메이션 · VFX · 사운드 · 히트박스처럼 **에셋 참조가 필요한 연출값**
  - 결과적으로 밸런스 패치는 클라이언트 재빌드 없이 로그인 시점 최신화만으로 반영됨
- **서버 주소 자동 탐지**
  - 시작 시 LAN IP를 **1초 타임아웃**으로 한 번 찔러보고, 응답하면 내부망 주소를, 실패하면 공인 IP를 채택
  - 주소를 인스펙터 상수로 두지 않고 커스텀 에디터에서 편집·저장하게 해서, 서버 환경이 바뀌어도 코드 수정이 없음
- **계정 해금은 64비트 비트마스크 한 컬럼으로**
  - 스킬이 60여 종이라 계정별 해금 테이블을 따로 두는 대신 `BIGINT` 한 칸에 담고, 타입별로 비트 구간을 예약(Active 1–19 / Passive 20–39 / Utility 40–60)
  - 스킬 카탈로그(전 계정 공통)와 개인 해금 상태(계정별)를 **명확히 다른 테이블로** 분리 — 카탈로그를 재구성해도 계정 데이터는 건드리지 않음
- **스킬 카탈로그는 공통 1 + 타입별 6 = 7테이블**
  - Active/Passive/Utility가 서로 다른 필드를 갖는데 한 테이블에 몰면 NULL 컬럼이 절반이 되므로, 타입별 기본 테이블과 레벨 테이블을 나눔(`(ability_id, level)` 복합 PK)
- **에디터 왕복 툴로 데이터 흐름을 양방향으로**
  - `AbilityUploadWindow` — 에디터에서 만든 스킬 SO를 서버로 업로드
  - `AbilityBakeWindow` — 서버 JSON을 받아 `.asset`으로 다시 구워, 서버가 꺼져 있어도 최신 밸런스로 작업 가능
- **세션·인증**
  - 로그인 시 세션 토큰과 해금 비트마스크를 함께 수신, 이후 15초 하트비트로 유효성 검사
  - `is_admin`을 서버가 권위적으로 판정 — 릴리즈 빌드의 디버그 기능을 클라이언트가 스스로 허용하지 못하게 함
- **팀에 넘길 규격을 문서로 고정** — 스킬 DB · 랭킹 · 크래시 리포트 · Admin · Sentry 스펙 문서 5종(총 989줄)을 작성해, 클라이언트가 실제로 파싱하는 필드명·타입 그대로 서버 구현이 맞춰지도록 함

> 📸 **[다이어그램]** ★최우선 — 두 서버 채널 분리도. Photon(실시간·휘발) / HTTP·MySQL(영속) 두 화살표와 각각이 나르는 데이터가 대비되게

> 📸 **[스크린샷]** 관리용 웹 — 스킬 수치 편집 화면 또는 랭킹/크래시 뷰어

> 📸 **[스크린샷]** `AbilityBakeWindow` 에디터 창 — 서버에서 받아온 스킬이 `.asset`으로 구워지는 화면

### (로그라이크) 3단 매니저 진행 파이프라인

#### 개요

로그라이크는 "보스를 늘리는 것"이 곧 콘텐츠를 늘리는 것인데, 층 이동·씬 로딩·난이도 스케일링이 한 클래스에 섞여 있으면 보스를 하나 추가할 때마다 진행 로직을 함께 고쳐야 합니다. 게다가 멀티플레이라 씬 전환과 난이도 적용 시점을 호스트가 주도해야 하는데, 이 책임까지 뭉치면 어디서 값이 결정됐는지 추적이 어려워집니다. **이를 해결하기 위해** 진행 책임을 **데이터 · 통제 · 현장** 세 층으로 나눠 파이프라인으로 구성했습니다.

#### 설계

- **`BossEncounterData` (ScriptableObject) — 데이터**
  - "이 보스는 이 맵에서 이 BGM으로 싸운다"를 한 덩어리로 묶은 순수 데이터. 로직을 일절 갖지 않음
- **`GameProgressionManager` — 통제 (런 동안 유지)**
  - 현재 층수 관리, 다음 보스 추첨, 파티 이동 지시. `DontDestroyOnLoad`로 런이 끝날 때까지 생존
  - 추첨은 완전 랜덤이 아니라 **셔플백** 방식 — 풀의 보스가 전부 한 번씩 나올 때까지 중복 없이 뽑고, 가방이 비면 다시 채움. 5층 중 같은 보스가 3번 나오는 사고를 구조적으로 막음
- **`BossArenaManager` — 현장 (각 보스 맵에 배치)**
  - 씬 로드가 끝나면 통제 매니저에게 층수를 묻고, 층수에 비례해 체력·데미지를 스케일링한 뒤 보스를 스폰
  - 접속 인원수에 따른 체력 보정도 **스폰 시점 기준**으로 적용 — 중간에 나간 인원이 자동으로 제외됨
- **전투 소요 시간은 전투 씬에서만 누적**
  - 이동 통로 씬·로비·엔딩은 측정에서 제외해, 랭킹 기록이 "실제로 싸운 시간"이 되게 함
  - 게스트는 스스로 누적하지 않고 **호스트가 내려준 값만** 사용 — 클라이언트별 시간 드리프트로 기록이 갈리는 것을 차단
- **확장 비용을 0으로**
  - 새 보스 추가 = SO 생성 → 통제 매니저의 Boss Pool에 등록 → 맵에 스폰 포인트 지정. **코드 수정 없음**
  - 현재 3스테이지 구성인 것은 보스가 3종이기 때문이며, 층수 상한은 값 하나로 관리

> 📸 **[다이어그램]** 3단 파이프라인 — 데이터(SO) → 통제(층수·추첨·이동) → 현장(스케일링·스폰), 각 단계가 무엇을 결정하는지 라벨과 함께

### (최적화) 이펙트 풀 + 셰이더 예열 로딩

#### 개요

전투 중 특정 이펙트가 **처음** 등장하는 순간 화면이 눈에 띄게 멈추는 현상이 있었습니다. 원인을 좁혀 보니 하나가 아니라 두 가지였는데, 커스텀 셰이더(피 이펙트·보스 왜곡 등)가 첫 렌더 시점에야 변형을 컴파일하는 것이 하나였고, 이펙트를 매번 `Instantiate`/`Destroy`하면서 첫 생성 시 텍스처·메시가 GPU에 업로드되고 GC가 발생하는 것이 다른 하나였습니다. **이를 해결하기 위해** 두 비용을 모두 로딩 화면 시점으로 앞당기고, 게임 중에는 미리 만들어 둔 인스턴스를 재사용하도록 구성했습니다.

#### 설계

- **셰이더 예열 — "실제로 쓰는 변형만" 컴파일**
  - 기록해 둔 `ShaderVariantCollection`을 `WarmUp()`으로 한 번에 컴파일
  - 그것만으로는 누락이 생기므로, 등록된 이펙트 프리팹을 **화면 밖 64×64 RenderTexture 카메라로 잠깐 렌더**해 그 이펙트가 실제로 사용하는 변형과 키워드를 강제로 컴파일하고 리소스를 GPU에 올림
  - 예열 중에는 프리팹의 게임 로직 스크립트(데미지·사운드·네트워크)를 꺼서 부작용 방지, 파티클만 재생 상태로 둠
  - 변형 컴파일 결과는 세션 동안 유지되므로 `HasWarmedUp` 플래그로 한 세션 1회만 수행
- **이펙트 풀 — 카테고리별 상한과 자동 회수**
  - 카테고리(BloodEffect / BossEffect / PlayerEffect …)마다 동시 활성 상한을 두고, 초과하면 `LinkedList` 앞쪽의 **가장 오래된 인스턴스를 회수해 재사용** — 상한이 없으면 난전에서 인스턴스가 무한히 늘어남
  - 카테고리 추가는 설정 에셋에 줄만 추가하면 되고 코드 수정이 필요 없음
  - `Spawn()`은 파티클 종료 시점(또는 지정 시간)에 자동으로 풀에 반납되어, 호출부가 회수를 신경 쓰지 않음
- **어느 씬에서 시작해도 존재하도록 부트스트랩**
  - `RuntimeInitializeOnLoadMethod`로 Resources의 풀 매니저 프리팹을 1회 자동 생성 + `DontDestroyOnLoad`
  - 로비에서 정상 진입하든, 디버그 단축키로 전투 씬에 직행하든 항상 동일하게 동작 — 씬마다 매니저를 배치할 필요가 없어짐
- **로딩 화면을 두 종류로 분리**
  - `scLoading` + `LoadingSceneController`: 예열·풀 사전 생성을 수행하는 실제 로딩 화면 (최소 노출 시간 보장)
  - `TransitionLoadingScreen`: 호스트가 시작한 네트워크 씬 전환을 가리는 커버. Fusion의 씬 로드 콜백을 받아 호스트/게스트 양쪽에서 자동 동작

> 📸 **[전/후 비교 2장]** ★최우선 — 프로파일러: 이펙트 최초 스폰 프레임의 스파이크(적용 전) vs 평탄해진 프레임(적용 후)

### (Trouble Shooting) 빌드가 3시간 넘게 걸리고, 고치려던 설정이 오히려 원인이었던 문제

#### 문제 상황

기능이 어느 정도 완성된 뒤부터 빌드 시간이 1시간을 넘기기 시작했고, 어느 시점부터는 **3시간이 지나도 끝나지 않아** 빌드를 중단해야 했습니다. 코드량이 늘어난 탓이라고 보기엔 증가폭이 비정상적이었고, 팀원 전원이 빌드를 한 번 돌릴 때마다 반나절을 잃는 상황이라 원인 규명이 급했습니다.

#### 문제와 해결

**[ 셰이더 배리언트 폭증 ]**

- **문제**: 빌드가 3시간을 넘겨 사실상 배포가 불가능했습니다.
- **원인 분석**: 빌드 로그에 셰이더별 배리언트 수를 남기도록 설정하고 확인한 결과, 셰이더 하나가 키워드 조합별로 수천 개씩 컴파일되고 있었습니다(한 셰이더에서 3,584개). 대부분은 **프로젝트가 빌트인 렌더 파이프라인에서 URP로 마이그레이션되며 남은 잔재**였습니다.
- **해결 과정**:
  1. URP Global Settings의 배리언트 로그 레벨을 켜서, 추측 대신 셰이더별 스트리핑 전/후 개수를 실측
  2. 에셋스토어 셰이더 그래프 3종에 **Built-In 타겟이 활성**으로 남아 있어 쓰지 않는 패스까지 컴파일되던 것을 제거 (URP만 남김)
  3. High 품질 렌더러만 Forward+였던 탓에 모든 셰이더가 Forward / Forward+ **두 계열을 전부** 컴파일하던 것을, Forward로 통일
  4. Decal 기법이 Automatic이라 DBuffer / ScreenSpace 두 세트를 다 컴파일하던 것을, PC에서 실제로 동작하는 DBuffer로 명시
  5. 샘플러 16개 한계를 넘겨 일부 배리언트 컴파일이 실패하던 그래프 3종에, **Sampler State 노드 하나를 만들어 모든 텍스처 샘플에 공유 연결**
- **결과**: 빌드 시간 **3시간 이상(중단) → 10분 미만**. 화면 결과물 변화는 없었습니다.
- **한계**: High 품질에서 Forward+를 포기했기 때문에 **오브젝트당 실시간 라이트 8개 제한이 부활**했습니다. 라이트가 밀집한 구역에서 일부 라이트가 무시될 수 있으나, 기본 품질이 Medium이라 대부분의 플레이어에게 영향이 없다고 판단해 빌드 시간을 택했습니다. 조명 문제가 보고되면 되돌릴 수 있도록 트레이드오프를 README에 명시해 두었습니다.

---

**[ 스트리핑 설정을 잘못 이해해 스스로 악화시킨 문제 ]**

- **문제**: 빌드 시간을 줄이려고 만진 설정 때문에 오히려 1시간이던 빌드가 3시간 이상으로 악화됐습니다.
- **원인**: Graphics 설정의 Lightmap/Fog Stripping 값을 `1`로 바꾸면 Automatic이 될 것이라 생각했으나, **`0`이 Automatic이고 `1`은 Custom(수동)** 이었습니다. Custom으로 바뀌면서 keep 플래그가 전부 켜진 상태가 되어, 스트리핑이 사실상 꺼져 버린 것이 진짜 원인이었습니다.
- **해결 과정**:
  1. "코드가 늘어서 느려졌다"는 가정을 버리고, 빌드가 느려지기 시작한 시점의 **설정 변경 이력**을 되짚음
  2. 두 값을 `0`(Automatic)으로 되돌려 씬 기준 자동 스트리핑을 복구
  3. Automatic이 **Build Settings에 등록된 씬을 기준으로** 유지 변형을 판단한다는 점을 확인하고, 누락돼 있던 전투 씬을 등록
  4. 같은 실수가 반복되지 않도록, 팀 공용 README에 "이 값을 Custom으로 바꾸지 말 것 / 새 씬은 반드시 Build Settings에 추가할 것"을 규칙으로 남김
- **결과**: 스트리핑이 정상 동작하도록 복구되어, 위 배리언트 정리와 합쳐 10분 미만 빌드를 달성했습니다.
- **한계**: 현재는 규칙을 문서로만 강제하고 있어, 설정이 되돌아가도 자동으로 감지되지 않습니다. 빌드 파이프라인에서 해당 값을 검증하는 프리빌드 훅을 넣는 것이 다음 개선안이지만, 팀 규모가 3인이라 문서 공유로 충분하다고 판단해 후순위로 두었습니다.

### (Trouble Shooting) 오브젝트 풀 도입 후 장판 데미지가 조용히 사라진 문제

#### 문제 상황

이펙트 풀을 적용한 뒤부터, 보스의 장판 공격이 **처음 한 번은 정상인데 두 번째부터 데미지가 들어가지 않는** 현상이 나타났습니다. 이펙트와 사운드는 정상적으로 재생돼서 눈으로는 문제가 보이지 않았고, 에러 로그도 남지 않아 "보스가 약해진 것 같다"는 체감으로만 보고되던 문제였습니다.

#### 문제와 해결

**[ 풀 재사용 시 초기화 누락 ]**

- **문제**: 풀에서 재사용된 장판이 데미지를 전혀 주지 않았습니다.
- **원인**: 판정이 끝나면 컴포넌트 자신을 `this.enabled = false`로 꺼서 멈추도록 되어 있었는데, 풀은 GameObject를 비활성/활성만 시키므로 **꺼진 컴포넌트에는 `OnEnable`이 다시 오지 않았습니다.** 그 결과 재사용 시 타이머와 피격 대상 목록이 초기화되지 않은 채 이미 종료된 상태로 남았습니다.
- **해결 과정**:
  1. 이펙트·사운드는 나오는데 데미지만 없다는 점에서, 스폰이 아니라 **판정 루프의 진입 조건**을 의심
  2. 컴포넌트를 끄는 방식이 풀 재사용과 충돌한다는 것을 확인
  3. 종료 표시를 `enabled` 대신 `_finished` 플래그로 바꾸고, 컴포넌트는 켜 둔 채로 판정만 멈추도록 변경
  4. `OnEnable`에서 타이머·피격 목록·판정 허용 플래그·종료 시각을 **매 재활성화마다** 초기화하도록 정리
  5. 원격 클라이언트는 `Initialize()`를 받지 않아 종료 시각이 0으로 남는 문제도 함께 발견해, `OnEnable`에서도 종료 시각을 계산하도록 보강
- **결과**: 풀에서 몇 번을 재사용해도 데미지가 정상 적용되며, 스폰 사운드도 매번 재생됩니다.
- **한계**: 얼음창 투사체는 자식 오브젝트에서 `Destroy(transform.root)`로 수명을 관리하고 있어 아직 풀에 편입하지 못했습니다. 풀 반환형으로 바꾸려면 내부 상태 3개의 리셋 시점을 다시 설계해야 하는데, **현재 정상 동작 중이고 생성 빈도가 낮아** 이득 대비 리스크가 크다고 판단해 보류했습니다.

**[ 겹쳐 깔린 장판의 중복 피해 ]**

- **문제**: 여러 장판을 촘촘히 깔아 두는 융단폭격 패턴에서, 겹치는 지점에 선 플레이어가 순식간에 죽었습니다.
- **원인**: 각 장판 인스턴스가 **자기 인스턴스 안에서만** 다단 히트 간격을 관리했기 때문에, 두 장판이 겹치면 같은 순간에 각각 한 번씩 총 두 배의 피해가 들어갔습니다.
- **해결 과정**:
  1. 인스턴스 내부의 다단 히트 간격과, 인스턴스 **사이**의 중복 방지는 별개 개념임을 정리
  2. AoE에 `overlapDamageGroup` 문자열 필드를 추가해, 같은 그룹으로 묶인 장판끼리만 정산하도록 함
  3. 그룹별 "플레이어가 마지막으로 피해를 받은 시각"을 static 딕셔너리로 인스턴스 간 공유하고, 간격 안이면 데미지만 건너뛰도록 처리
  4. 사운드와 히트 연출은 그대로 재생되게 남겨, 판정만 줄었을 뿐 타격 피드백은 유지
  5. 그룹 이름을 비워 두면 기존처럼 독립 판정하도록 해서, 기존 패턴들이 영향을 받지 않게 함
- **결과**: 겹친 구역에서도 지정한 간격당 한 번만 피해가 들어가, 융단폭격 패턴의 밸런스를 의도대로 조정할 수 있게 됐습니다.
- **한계**: 그룹을 문자열로 식별하므로 **오타가 나면 조용히 독립 판정으로 되돌아갑니다.** 또 static 딕셔너리라 씬 전환으로 파괴된 플레이어 참조가 남아 정리 로직을 따로 넣어야 했습니다. 그룹을 enum이나 SO 참조로 바꾸는 것이 안전하지만, 현재 그룹이 소수라 후순위로 두었습니다.

### (Trouble Shooting) 2페이즈 진입 후 보스가 한 대만 맞아도 즉시 그로기에 걸린 문제

#### 문제 상황

플레이어가 그로기(무력화) 게이지를 다 채워 보스를 무너뜨린 상태에서, 그 딜 타임 동안 보스 체력이 50% 아래로 떨어지면 2페이즈로 전환됩니다. 그런데 이렇게 전환된 경우에 한해, **2페이즈에 들어서자마자 보스가 한 대만 맞아도 다시 그로기에 걸려** 광폭화 패턴을 거의 쓰지 못하고 쓰러졌습니다. 재현 조건이 "그로기 중에 정확히 50% 컷을 낸다"로 좁아서 원인을 찾는 데 시간이 걸렸습니다.

#### 문제와 해결

**[ 상태 전이가 다른 상태의 정리 코드를 건너뛴 문제 ]**

- **문제**: 그로기 중 페이즈 전환이 일어나면 그로기 게이지가 가득 찬 채로 2페이즈가 시작됐습니다.
- **원인**: 그로기 게이지 초기화가 **그로기 상태의 정상 종료 분기에서만** 수행되고 있었는데, 페이즈 전환이 상태를 `PhaseTransition`으로 덮어쓰면서 그 분기가 영영 실행되지 않았습니다. 게이지는 최대치를 유지한 채 남았고, 이후 한 번의 피격만으로 다시 임계값을 넘겼습니다.
- **해결 과정**:
  1. "2페이즈 로직 오류"라는 첫 가정을 접고, 재현 조건이 그로기 중일 때뿐이라는 점에서 **상태 전이 순서**를 의심
  2. 그로기 종료 처리와 페이즈 전환 처리가 서로 다른 위치에 있고, 후자가 전자를 무효화한다는 것을 확인
  3. 페이즈 전환 시점에서 그로기 게이지를 명시적으로 초기화하도록 정리하고, 그 이유를 코드 주석으로 남김
  4. 같은 성격의 누락을 막기 위해, 패턴 인덱스 리셋처럼 상태를 벗어날 때 필요한 정리는 **상태 전이 함수 한 곳에서 공통 처리**하도록 옮김
- **결과**: 그로기 중에 페이즈 컷이 나도 2페이즈는 빈 게이지로 시작하며, 광폭화 패턴이 의도대로 전개됩니다.
- **한계**: 근본적으로는 상태별 진입/퇴장 훅이 없어서 정리 코드가 전이 지점마다 흩어질 수 있는 구조입니다. 상태를 개별 클래스로 분리하면 해결되지만 보스 3종이 모두 이 코어를 상속하고 있어 변경 범위가 커서, 남은 일정에서는 공통 전이 함수로 모으는 선까지만 진행했습니다.

### (Trouble Shooting) 중복 로그인 차단과, 세션 종료 시 살아나는 좀비 매니저

#### 문제 상황

같은 계정으로 두 곳에서 동시에 접속하면 해금 상태와 랭킹 기록이 서로 덮어써졌습니다. 그리고 세션 만료로 네트워크를 종료하는 과정에서, 이미 파괴된 매니저를 다른 매니저가 참조하며 **종료 중에 새 매니저 오브젝트가 생성되는** 오류가 함께 발생했습니다.

#### 문제와 해결

**[ 같은 계정 중복 접속 ]**

- **문제**: 동일 계정 동시 접속 시 서버 데이터가 나중 저장 순서대로 덮어써졌습니다.
- **원인**: 로그인 성공 여부만 확인하고 **접속 상태를 서버가 추적하지 않아**, 이전 접속이 여전히 유효한 클라이언트로 남아 있었습니다.
- **해결 과정**:
  1. 유저 테이블에 세션 토큰 컬럼을 추가하고, 로그인 성공 시 **마지막 로그인만 유효 토큰**이 되도록 갱신
  2. 클라이언트가 로그인 직후 하트비트 코루틴을 켜서 15초마다 세션 유효성을 확인
  3. 토큰이 더 이상 자기 것이 아니면 세션 만료 이벤트를 발행하도록 처리
- **결과**: 뒤늦게 접속한 쪽만 유효해지고, 기존 접속은 다음 하트비트에서 스스로 정리됩니다.
- **한계**: 최대 **15초의 감지 지연**이 있어 그 사이에는 두 클라이언트가 공존합니다. 주기를 줄이면 서버 요청이 선형으로 늘어나는데, 이 게임에서 15초 사이에 덮어쓸 만한 저장 시점(클리어·해금)이 발생할 확률이 낮다고 판단해 현재 주기를 유지했습니다.

**[ 종료 중 되살아나는 싱글톤 ]**

- **문제**: 애플리케이션 종료나 세션 만료로 매니저들이 파괴되는 도중, 이미 파괴된 매니저에 접근하면서 **새 GameObject가 생성되고** 오류가 발생했습니다.
- **원인**: 싱글톤의 `Instance` 접근자가 인스턴스가 없으면 무조건 새로 생성하도록 되어 있어서, **파괴 콜백에서의 접근까지 생성 요청으로 처리**됐습니다.
- **해결 과정**:
  1. 매니저마다 흩어져 있던 싱글톤 보일러플레이트를 제네릭 `MonoSingleton<T>` 하나로 통합
  2. 종료 중임을 표시하는 플래그를 두고, 종료 중 `Instance` 접근은 생성 대신 `null`을 반환하도록 변경
  3. 파괴 콜백에서 쓸 `HasInstance` 프로퍼티를 제공해, 구독 해제 시 인스턴스를 되살리지 않도록 함
  4. 백엔드와 네트워크가 서로를 직접 참조하던 것을 `SessionGuard` + `ISessionGuard` 인터페이스로 끊어, 세션 만료 → 네트워크 종료 경로를 **한 컴포넌트로 격리** **(의존성 역전)**
- **결과**: 종료·세션 만료 경로에서 좀비 오브젝트 생성이 사라졌고, 네트워크 레이어를 백엔드 없이도 단독으로 테스트할 수 있게 됐습니다.
- **한계**: `OnApplicationQuit`을 기준으로 삼기 때문에 **에디터에서 플레이 모드를 강제 중단하는 경우** 등 일부 경로는 여전히 커버되지 않습니다. 실제 빌드에서는 재현되지 않아 후순위로 두었습니다.

## 개발 과정에서의 AI 활용

구조 설계와 기술 판단은 직접 하되, **판단에 필요한 정보를 모으는 단계**와 **결정한 내용을 팀에 넘기는 단계**에 AI를 활용했습니다. 특히 3인 팀에서 서버 파트를 혼자 맡다 보니, 팀원에게 넘길 규격을 빠짐없이 문서화하는 작업의 비중이 컸습니다.

- **인수인계 문서 작성** — 서버 구현 스펙 5종(스킬 DB · 랭킹 · 크래시 · Admin · Sentry)과 보스 제작 가이드를, 제가 정한 규격을 기준으로 초안을 만든 뒤 실제 코드가 파싱하는 필드명·타입과 일일이 대조해 확정
- **원인 후보 좁히기** — 빌드 시간 문제처럼 후보가 많은 사안에서, 확인해야 할 지점 목록을 뽑는 용도로 사용. 실제 판단은 빌드 로그의 배리언트 실측값으로 내렸습니다
- **작업 규칙 고정** — 반복되는 분석 낭비를 줄이려고 `AGENTS.md`에 "전체 리포지토리를 훑지 말고 의존 경로만 완전히 읽을 것" 같은 규칙을 정의해 두고 사용
- **발표 자료 제작** — 웹 기반 발표 덱의 마크업/스타일 초안

AI가 제안한 결과를 그대로 반영하지 않고, **셰이더 스트리핑 값의 의미처럼 실제로 되물어 확인해야 하는 부분은 직접 실측한 뒤** 선별 적용했습니다. 위 트러블슈팅에 적은 "설정값을 잘못 이해해 스스로 악화시킨 사례"가 그 검증 과정에서 밝혀진 것입니다.
