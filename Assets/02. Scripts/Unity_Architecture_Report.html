ServerSouls - Unity 아키텍처 리포트

약 94개의 커스텀 .cs 스크립트(Assets/02. Scripts 기준)에 대한 정적 분석 결과입니다. 외부 플러그인은 자동 제외했으며, 클래스 시그니처/상속/필드/컴포넌트 룩업/싱글톤 접근을 기준으로 의존성을 추출했습니다.

1. 전체 아키텍처 개요

ServerSouls는 3인 협동 보스러시 게임으로, Unity + Photon Fusion(호스트 권한 모델) 위에 자체 PHP 백엔드를 결합한 구조입니다. 코드베이스는 기능 도메인(Player / Boss / HUD / Reward / Stage / Options / DB / Server)으로 명확히 분리되어 있고, Manager 싱글톤 패턴이 횡단 관심사(네트워크, 사운드, 설정, 진행도, 컷씬, 카메라, 능력치, 백엔드, 기믹)를 9곳에서 조율합니다. 게임 데이터는 ScriptableObject로 외부화되어 있으며(PlayerAbilityModule, BossPatternModule, BossEncounterData, StatusEffectData, SettingData, AbilityAssetDatabase), 이것이 프로젝트의 가장 강력한 디커플링 메커니즘입니다.

아키텍처의 압력 지점은 두 개의 "갓 NetworkBehaviour"에 집중되어 있습니다 - NetworkPlayerController(1300+ 라인, 7개 이상의 동일 GameObject 컴포넌트 참조)와 NetworkBossCore(650+ 라인, 상태/패턴/상태이상 DB/비주얼 위임을 모두 보유). HUD/Reward 계층은 매 프레임 FindObjectsOfType<NetworkPlayerController>를 호출해 플레이어를 재발견하고 있어, 중앙 플레이어 레지스트리가 없음을 보여줍니다.

3. 네트워크 & DB 통합 분석

ServerSouls는 두 개의 외부 시스템과 통신합니다: (1) Photon Fusion Cloud로 실시간 게임플레이를 동기화하고, (2) 자체 호스팅 PHP 백엔드(MySQL/MariaDB로 추정)로 인증/스킬 잠금해제 데이터를 영속화합니다. 두 통신은 완전히 분리되어 있으며 - 게임 시작 전 단계에서 PHP로 인증 + 스킬 DB를 모두 로드한 후, 게임 진입 후엔 Photon만 사용합니다.

3-1. PHP REST API 백엔드

BackendManager(싱글톤)가 모든 HTTP 통신을 담당합니다. UnityWebRequest + WWWForm(POST)으로 PHP 서버에 요청을 보내고, 응답은 JsonUtility.FromJson으로 파싱합니다. 주목할 특징:

  • LAN/WAN 자동 탐지 - 게임 시작 시 log_viewer.php를 1초 타임아웃으로 핑하여, 같은 공유기 내부에 있으면 LAN IP(192.168.0.5)를, 아니면 공인 IP(1.233.102.137)를 사용합니다. 베이스 URL은 모두 http://{IP}:8080/soulrush_api/ 형식입니다.
  • 세션 토큰 + 하트비트 - 로그인 성공 시 PHP가 session_token을 발급하고, 클라이언트는 15초마다 check_session.php를 호출해 "invalid" 응답을 받으면 중복접속 처리로 강제 로그아웃됩니다. 이 이벤트는 OnSessionExpired로 발행되어 NetworkManager가 구독, Photon 런너를 셧다운한 뒤 로그인 씬으로 강제 이동시킵니다.
  • 64비트 스킬 비트마스크 - 유저가 잠금해제한 스킬은 BIGINT 한 컬럼(unlocked_skills)에 비트마스크로 저장됩니다. 클라이언트는 AbilityManager.GetUnlockedAbilitiesList(long userBitmask)로 비트 AND 연산하여 보유 스킬을 복원합니다. 최대 64개 스킬까지 확장 가능한 설계입니다.
  • 라이브 데이터 패치 - get_abilities.php가 반환한 최신 데미지/쿨타임 값으로 Resources에서 로드한 PlayerAbilityModule(ScriptableObject)을 InitializeFromDB로 덮어씁니다. "클라이언트 패치 없이 밸런스 조정 가능"한 핵심 메커니즘입니다.

3-3. Photon Fusion 실시간 네트워크 흐름

Photon Fusion은 호스트 권한(Host Authority) 모델을 사용합니다. NetworkManager가 NetworkRunner를 생성/관리하고, GameMode는 솔로 플레이(Host), 자동 매칭(AutoHostOrClient), 코드 입장(AutoHostOrClient+세션명) 세 가지로 분기합니다. 방장 클라이언트가 모든 상태 권한(StateAuthority)을 가지며, 나머지는 입력만 제출합니다(NetworkInputProvider+NetworkInputData).

  • 로비 - LobbyServerManager가 슬롯 3개(Slot0_Owner~Slot2_Owner) + 레디 상태를 [Networked] 변수로 동기화. RPC_ToggleReady로 레디 토글, OnClickBattleButton으로 방을 잠그고(IsVisible=false, IsOpen=false) 보스 씬 진입.
  • 보스 아레나 - BossArenaManager가 INetworkRunnerCallbacks로 입장한 플레이어를 스폰. 이전 씬의 플레이어 오브젝트가 살아 있으면 위치만 이동시켜 세션 상태(PlayerSessionStore 스냅샷, PlayerAbilityInventory)를 복원.
  • 층수 증가 - GameProgressionManager.CurrentLevel은 호스트가 권한을 가지고, BossArenaManager.NetworkedStageLevel로 클라이언트에 브로드캐스트. 보스의 HP/데미지가 (level-1) × 0.2~0.1씩 증가.
  • 씬 전환 - NextLevelPortal.OnTriggerEnter가 호스트 권한일 때 GameProgressionManager.GoToNextLevel(runner)을 호출. 모든 플레이어 스탯이 PlayerSessionStore에 스냅샷되어 새 씬에서 복원됨.

3-4. 통신 흐름 시퀀스 다이어그램

[게임 시작] Unity Client └─▶ BackendManager.AutoDetectServerRoutine() └─▶ GET log_viewer.php (1s timeout) → LAN/WAN 자동 결정 BASE_URL = http://{IP}:8080/soulrush_api/ [로그인] LoginSceneController └─▶ BackendManager.LoginUser(id, pw) └─▶ POST login.php ⇐ AuthResponse { nickname, unlocked_skills (BIGINT), session_token } 캐싱: CurrentLoginID / CurrentNickname / CurrentSkillsBitmask / CurrentSessionToken └─▶ StartCoroutine(HeartbeatRoutine) // 15초 간격 무한 루프 └─▶ AbilityManager.FetchAbilities() └─▶ GET get_abilities.php ⇐ AbilityDBResponse { data: [{ bit_index, damage_multiplier, ... }] } Resources.Load<PlayerAbilityModule>("GeneratedAbilities/{ability_id}") → bakedModule.InitializeFromDB(dbData) // 라이브 밸런스 패치 [하트비트 (15초 주기)] BackendManager.HeartbeatRoutine └─▶ POST check_session.php { login_id, session_token } 만약 응답에 "invalid" 포함: └─▶ OnSessionExpired 이벤트 발행 └─▶ NetworkManager.HandleSessionExpired ├─▶ Runner.Shutdown() └─▶ SceneManager.LoadScene("scLogin") [게임플레이 (Photon Fusion)] TitleManager.OnClickAutoMatch └─▶ NetworkManager.StartAutoMatch() └─▶ Runner.StartGame(GameMode.AutoHostOrClient) Runner.LoadScene("scLobbyMain") // 호스트만 LobbyServerManager // NetworkBehaviour, ChangeDetector [Networked] Slot0/1/2_Owner, Slot0/1/2_Ready OnClickBattleButton (호스트만) └─▶ SessionInfo.IsVisible = false; IsOpen = false // 방 잠금 └─▶ GameProgressionManager.StartFirstLevel(Runner) └─▶ Runner.LoadScene("scBossArena_L1") BossArenaManager.Spawned (호스트) ├─▶ SpawnPlayer × N // 이전 씬 오브젝트는 위치만 이동 └─▶ Runner.Spawn(bossPrefab) + 층수 보정(HP/Damage 배율) [스킬 데이터 저장] (보스 보상 획득 시점) └─▶ BackendManager.UpdateSkills(newBitmask) └─▶ POST update_skills.php { login_id, unlocked_skills, session_token } ⇐ SkillResponse { status, updated_skills }
관찰 - PHP 백엔드와 Photon은 서로를 직접 모릅니다. 둘 사이의 유일한 연결점은 NetworkManager → BackendManager.OnSessionExpired 이벤트 구독 한 줄로, 백엔드 세션이 만료되면 Photon 런너를 강제 종료하는 단방향 흐름입니다. 덕분에 게임플레이 도중에는 PHP 의존성이 거의 없고(스킬 저장 호출 정도), 인터넷이 잠시 끊겨도 하트비트 통신 실패는 무시됩니다.

4. 주요 아키텍처 발견사항

핫스팟 - NetworkPlayerController (갓 오브젝트). 약 1300줄 규모. 동일 GameObject의 7개 컴포넌트 (PlayerStats, PlayerStatusController, PlayerAbilityInventory, PlayerAbilityRewardController, LockOnTargetSelector, NetworkCharacterController, Animator)를 캐싱하고, 외부로는 CameraManager, BossHitbox, NetworkBossCore, GimmickAltar까지 직접 접근합니다. 개선안: Input / Movement / Combat / NetworkSync 4개 partial 또는 NetworkBehaviour로 분할하고, InputContext 구조체를 이벤트로 브로드캐스트하면 됩니다.
핫스팟 - NetworkBossCore (갓 오브젝트). 약 650줄. 페이즈 로직, 패턴 선택, 상태이상 데이터베이스, 데미지 적용, 비주얼 인터페이스(IBossVisual), 기믹 라이프사이클을 모두 보유. 파생 클래스는 DragonBoss 단 하나뿐이라, 추상화 자체가 전략 패턴의 역할을 하고 있는지 재검토가 필요합니다.
싱글톤 난립. 9개 싱글톤 중 2개만 제네릭 MonoSingleton<T>를 상속하고, 나머지 7개는 같은 패턴을 수동으로 다시 구현합니다. NetworkManager, BackendManager, GameSettingsManager, GameProgressionManager, CutsceneManager, ScenePrefabManager, CameraManager, CameraPointManager, DragonArenaGimmick을 MonoSingleton<T> 기반으로 통일하는 것을 권장합니다.
FindObjectsOfType 남용 - 발견 메커니즘 부재. HUDManager(3회), RewardManager(4회), ReviveUIManager, InventoryPanelController, CutsceneManager, CameraManager, DragonBossOrigin에서 매번 O(n) 씬 스캔이 발생합니다. NetworkPlayerController.Spawned() / Despawned()에서 갱신되는 플레이어 정적 레지스트리를 도입하면 위 호출이 모두 제거됩니다.
네트워크 ↔ 백엔드 교차 의존성. NetworkManager가 BackendManager.OnSessionExpired를 직접 구독해 Photon 런너를 셧다운합니다. 현재는 한 줄짜리 약한 결합이지만, ISessionGuard 같은 인터페이스로 추상화해두면 백엔드 없이 네트워크 레이어만 테스트할 수 있게 됩니다.
레거시 중복 코드 의심. DragonBossOrigin과 DragonVisualOrigin은 활성 경로(DragonBoss/DragonVisual)와 필드 구성이 거의 동일합니다. BossArenaManager가 스폰하는 프리팹이 NetworkBossCore 기반이므로, *Origin 클래스가 더 이상 어떤 프리팹에도 연결되지 않았는지 확인 후 제거를 검토하세요.
유지해야 할 좋은 패턴. ScriptableObject 기반 데이터 주도 설계(능력/패턴/조우/상태이상/설정), NetworkBossCore ↔ IBossVisual의 상태/비주얼 분리, 이벤트 기반 보상 흐름(BossRewardOffered), 씬 간 스냅샷 저장(PlayerSessionStore), HUD의 View/DTO 분리(PlayerHUDView + PlayerHUDData), PHP 라이브 패치(InitializeFromDB로 데미지/쿨타임 핫리로드).

6. 계층형 의존성 그래프

노드는 클래스/데이터 타입이며 카테고리별 색상으로 구분됩니다. 레이아웃은 위에서 아래로(Up-Down) 흐르는 계층형(Hierarchical)이고, 물리 엔진은 비활성화되어 노드가 흔들리지 않습니다. 사소한 의존성(SoundManager 호출, 씬 페이드, 디버그/에디터 스크립트, 단순 비주얼 트리거)은 그래프 명료성을 위해 의도적으로 제외했습니다.

※ 화살표 방향: A → B 는 "A가 B에 의존한다"는 의미입니다. 노드를 클릭하면 연결된 클래스만 강조됩니다.

  2. NetworkPlayerController 분할. 입력 파싱 → PlayerInputRouter, 전투 히트 감지 → PlayerCombatController로 분리. 본 클래스는 [Networked] 프로퍼티만 보유하는 얇은 코디네이터로 남기세요.
  3. 싱글톤 통일. 9개 중 7개가 패턴을 수동 재구현 - 모두 MonoSingleton<T>를 상속하도록 통일하면 코드 중복이 사라집니다.
  4. 레거시 *Origin 정리. DragonBossOrigin / DragonVisualOrigin이 어떤 프리팹에도 연결되어 있지 않다면 제거 - 보스 서브시스템의 인지 부담이 절반으로 줄어듭니다.
  5. IBossVisual 활용 확대. 두 번째 비-드래곤 보스를 추가해 추상화를 검증하세요. 현재는 구현체가 하나뿐이라 이론적인 인터페이스입니다.
  6. 네트워크 ↔ 백엔드 결합 완화. BackendManager가 도메인 이벤트만 발행하고, 작은 SessionGuard 컴포넌트가 그것을 받아 Photon 런너를 종료하도록 분리하세요.
  7. HTTP 보안 보강. 현재 모든 PHP 통신이 평문 HTTP(:8080)입니다. 비밀번호 + session_token이 그대로 전송되므로, HTTPS 종단(Nginx 리버스 프록시 + Let's Encrypt) 적용이 시급합니다.
